# Database

The full schema lives in [`supabase/migrations/001_initial_schema.sql`](../supabase/migrations/001_initial_schema.sql) and is meant to be run once, in order, against a fresh Supabase project's SQL Editor. Optional demo data is in [`supabase/seed.sql`](../supabase/seed.sql), kept in a separate file so it is never confused with application logic.

## Tables

### `profiles`

One row per Supabase Auth user, created automatically. Stores app-level fields that `auth.users` doesn't: display name, a cached copy of the email, and the role used for authorization.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | Same value as `auth.users.id`; cascades on delete. |
| `full_name` | text | Defaults to `''`, editable by the user. |
| `email` | text | Copied from `auth.users.email` at sign-up so admins can identify registrants without ever querying the `auth` schema from the frontend. |
| `role` | text | `'user'` or `'admin'`, enforced by a `check` constraint. Defaults to `'user'`. |
| `created_at`, `updated_at` | timestamptz | Maintained automatically. |

### `events`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | Generated by `gen_random_uuid()`. |
| `title`, `description`, `location`, `category` | text | Required. |
| `event_date` | date | Required. |
| `start_time`, `end_time` | time | Required; a `check` constraint enforces `end_time > start_time`. |
| `capacity` | integer | Required; must be `> 0`. |
| `image_url` | text | Optional. |
| `status` | text | `upcoming` \| `ongoing` \| `completed` \| `cancelled`, defaults to `upcoming`. |
| `created_by` | uuid, FK → `profiles(id)` | Nullable; set null if the creating admin's account is deleted. |
| `created_at`, `updated_at` | timestamptz | Maintained automatically. |

### `registrations`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | |
| `event_id` | uuid, FK → `events(id)`, `on delete cascade` | |
| `user_id` | uuid, FK → `profiles(id)`, `on delete cascade` | |
| `status` | text | `registered` \| `cancelled`, defaults to `registered`. |
| `registered_at` | timestamptz | Defaults to `now()`. |

A **unique constraint on `(event_id, user_id)`** means a user has at most one registration row per event, ever — cancelling and re-registering re-uses the same row instead of creating a new one.

## Triggers and functions

| Name | Fires on | Purpose |
|---|---|---|
| `handle_new_user` | `after insert` on `auth.users` | Creates the matching `profiles` row automatically when someone signs up. |
| `set_updated_at` | `before update` on `profiles`, `events` | Keeps `updated_at` current. |
| `prevent_role_escalation` | `before update` on `profiles` | If a logged-in non-admin tries to change their own `role` column, silently resets it to the old value. Defense in depth: RLS alone cannot restrict which *columns* an update touches. Only applies when `auth.uid()` is set (i.e. the request came through an authenticated session) — direct SQL run by the project owner, such as promoting the first admin from the SQL Editor, has no `auth.uid()` and is intentionally exempt. |
| `enforce_registration_rules` | `before insert or update` on `registrations` | Rejects the write if the target event is cancelled, or if it's already at capacity. Runs regardless of whether the request came through the UI, so it also protects against two users racing for the last spot. |
| `is_admin()` | called by RLS policies | `security definer` helper that checks `profiles.role` for the current user without recursively re-triggering the `profiles` RLS policy that itself calls `is_admin()`. |

## Row Level Security (RLS)

RLS is enabled on all three tables. Policies:

| Table | Operation | Who | Policy logic |
|---|---|---|---|
| `profiles` | SELECT | Owner or admin | `auth.uid() = id OR is_admin()` |
| `profiles` | UPDATE | Owner only | `auth.uid() = id` (role changes blocked by the trigger above) |
| `profiles` | INSERT / DELETE | Nobody (no policy) | Rows are only created by the `handle_new_user` trigger and removed via cascade from `auth.users`. |
| `events` | SELECT | Everyone (including anonymous) | `true` |
| `events` | INSERT / UPDATE / DELETE | Admin only | `is_admin()` |
| `registrations` | SELECT | Owner or admin | `auth.uid() = user_id OR is_admin()` |
| `registrations` | INSERT | Self only | `auth.uid() = user_id` — a user cannot insert a registration for someone else. |
| `registrations` | UPDATE | Owner or admin | `auth.uid() = user_id OR is_admin()` |
| `registrations` | DELETE | Nobody (no policy) | Cancellation is a status change, not a deletion. |

Because these rules live in PostgreSQL itself, they hold even if someone bypasses the React app entirely and calls the Supabase REST API directly with their own access token — which is exactly what [`11-testing.md`](11-testing.md) verifies.

## Why no `service_role` key in the frontend

The `service_role` key bypasses RLS entirely and must never be exposed to a browser. This project only ever uses the public **anon** key on the client (see `.env.example`); every access-control decision is made by RLS policies evaluated against the logged-in user's own token, not by which key was used to connect.
